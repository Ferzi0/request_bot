## Что это и зачем

Клиент приходит в бота (с сайта по кнопке «Заявка через Telegram-бота» или сам), отвечает на пять вопросов — те же, что в форме на сайте, — и отправляет заявку. Заявка сохраняется в базу и приходит **администратору** (заказчику, `ADMIN_ID`) в личный чат с ботом. Администратор берёт её в работу кнопкой или через панель `/admin`, и клиенту приходит сообщение «заявка принята в работу».

```
клиент ──/start──▶ диалог (5 шагов) ──▶ сводка ──«Отправить»──▶ заявка
                                                                 │
                         ┌───────────────────────────────────────┤
                         ▼                                       ▼
                 SQLite data/bot.db                 сообщение администратору
                 (status = new)                     «Новая заявка № …» + кнопки
                         ▲                                       │
                         │        «✅ В работу» или /admin → карточка → «🔧 В работу»
                         └──────────── status = in_work ◀────────┘
                                             │
                                             ▼
                          клиенту: «🔧 Заявка № … принята в работу»
```

## Возможности

**Клиент**
- Диалог из пяти шагов: имя → почта или Telegram → тип проекта → задача → согласие на обработку данных; затем сводка с кнопками «Отправить / Изменить / Отмена».
- Подсказки-кнопки: «Использовать имя из Telegram», «Ответить мне в Telegram» (подставит `@ник`).
- Ответ «✅ Заявка принята» с номером `ГГММДД-XXXX`; позже — «🔧 Заявка № … принята в работу».
- Если заявку не удалось переслать — честное сообщение и запасной контакт (`FALLBACK_CONTACT`).
- `/start`, `/help`, `/cancel` работают на любом шаге; ссылка с сайта `t.me/<бот>?start=site` помечает источник «сайт».

**Администратор**
- Каждая заявка — сообщение с данными клиента и кнопками «Написать клиенту» и «✅ В работу».
- Панель `/admin` (видна только ему): счётчики по статусам, списки по 5, карточка заявки, смена статуса, отмена с подтверждением.
- Уведомления в чат о состоянии базы: при запуске, при сбое записи заявки или статуса.
- Пункт «Админ-панель» в меню команд только в его чате.

## Быстрый старт

**Требования:** Python **3.12–3.14** (`requires-python = ">=3.12,<3.15"` в `pyproject.toml`; проверялся только 3.14), [uv](https://docs.astral.sh/uv/) (или `pip`), аккаунт Telegram.

1. **Окружение** — зависимости зафиксированы в `uv.lock`:

   ```bash
   uv sync                       # создаст .venv и поставит всё, включая dev-инструменты
   # без uv:  python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
   ```

   `requirements.txt` — экспорт из lock без dev-зависимостей (тесты и линтеры ставятся только через `uv sync`). После изменения зависимостей: `uv lock && uv export --format requirements-txt --no-dev --no-hashes -o requirements.txt`.

2. **Бот в Telegram.** В [@BotFather](https://t.me/BotFather): `/newbot` → имя и username → скопируйте токен вида `123456789:AAE…`. Имя бота задаёте вы; описание («Что умеет этот бот?») бот выставит сам при запуске.

3. **Ваш ID** — напишите [@userinfobot](https://t.me/userinfobot), он ответит числом. Это `ADMIN_ID`.

4. **Настройки:**

   ```bash
   cp .env.example .env          # впишите BOT_TOKEN и ADMIN_ID, остальное — по желанию
   ```

5. **Откройте своего бота и нажмите /start.** Без этого бот не сможет написать вам первым — ни заявки, ни уведомления.

6. **Запуск** (остановка — Ctrl+C):

   ```bash
   .venv/bin/python -m bot
   ```

   При старте бот открывает базу (и при необходимости обновляет её схему), проверяет токен (`getMe`), снимает webhook **без** сброса накопившихся апдейтов (заявки, пришедшие, пока бот был выключен, не теряются), ставит меню команд и описание и присылает вам «Бот запущен и готов принимать заявки.» со строкой о базе: «База данных: работает (схема v4, заявок: N).» или «⚠️ База данных недоступна…».

7. **Первая проверка:** напишите боту `/start` с другого аккаунта (или со своего — путь клиента у администратора тот же), пройдите диалог, отправьте заявку — она придёт вам, клиенту — «✅ Заявка принята».

## Настройки .env

Файл `.env` ищется в папке проекта (не в текущем каталоге), в git не попадает. Пустое значение (`POLICY_URL=`) — то же, что «не задано». Переменные окружения с теми же именами имеют приоритет над `.env`. Неверное значение — понятная русская ошибка при запуске, код выхода 2, без трейсбека; значение токена в ошибку не попадает.

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `BOT_TOKEN` | да | — | токен от @BotFather; проверяется форма `цифры:символы` |
| `ADMIN_ID` | да | — | ваш числовой Telegram ID: сюда приходят заявки, только вам доступны «В работу» и `/admin` |
| `POLICY_URL` | нет | пусто | ссылка на политику конфиденциальности в шаге согласия (`https://…`); пусто — текст без ссылки |
| `FALLBACK_CONTACT` | нет | пусто (в `.env.example` — почта и ник с сайта) | контакт для клиента, если заявку не удалось переслать |
| `TIMEZONE` | нет | `Asia/Yekaterinburg` | пояс для времени в сообщениях и даты в номере заявки (в базе время всегда UTC) |
| `APPLICATIONS_PER_HOUR` | нет | `3` | сколько доставленных заявок в час можно отправить с одного Telegram-аккаунта |
| `NOTIFY_ADMIN_ON_START` | нет | `true` | присылать «Бот запущен…» при старте; о недоступной базе бот пишет всегда |
| `LOG_LEVEL` | нет | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` |
| `DATABASE_PATH` | нет | `data/bot.db` | файл базы; относительный путь — от папки проекта, `~` раскрывается |

Служебные (обычно не трогают):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SEND_RETRY_DELAYS` | `[1, 3]` | паузы (с) между попытками отправить заявку вам, списком в квадратных скобках (JSON): `[1, 3]` = 3 попытки; `1,3` без скобок — ошибка настройки |
| `NAME_MIN`, `NAME_MAX` | `2`, `80` | длина имени |
| `CONTACT_MAX` | `120` | длина контакта |
| `TASK_MIN`, `TASK_MAX` | `10`, `1000` | длина задачи |

Лимиты совпадают с формой сайта — меняйте вместе с ней. Слишком большой `TASK_MAX` (примерно больше 2000) может не уместиться в лимит Telegram 4096 символов на сообщение.

## Как работает диалог

**Шаги** (`bot/states.py`, обработчики — `bot/handlers/application.py`):

| Состояние FSM | Что спрашиваем | Проверка |
|---|---|---|
| `name` | как обращаться | 2–80 символов |
| `contact` | почта или Telegram | почта, `@ник` или `t.me/ник` (те же выражения, что на сайте); ник и ссылка приводятся к `@ник`; до 120 |
| `project_type` | тип проекта — кнопкой | Сайт-визитка, Лендинг, Telegram-бот, Веб-сервис, Интернет-магазин, Другое |
| `task` | задача в двух-трёх фразах | 10–1000 символов, только текст |
| `consent` | согласие — кнопкой «Даю согласие» | — |
| `confirm` | сводка: «Отправить / Изменить / Отмена» | — |
| `choose_field` | «Изменить»: какое поле поправить | после ввода — сразу снова сводка |

Ошибка ввода — короткое сообщение с причиной («81 символ при лимите 80 символов»), шаг не меняется, ввод не обрезается молча. Черновик хранится в данных FSM (`bot/drafts.py`), номер заявки выдаётся при первой попытке отправки и сохраняется при повторе — дубль у вас будет узнаваем по номеру.

**Защита:**
- **Санитайзер** (`bot/services/validation.py`): убирает управляющие и невидимые символы (zero-width, bidi-переключатели вроде U+202E), схлопывает пробелы, нормализует Unicode (NFC).
- **Только личные чаты** — `PrivateChatOnlyMiddleware` на сообщениях и кнопках: в группах бот молчит.
- **Очередь апдейтов одного пользователя** — `SimpleEventIsolation` в `bot/app.py`: два быстрых сообщения или двойное нажатие «Отправить» обрабатываются по очереди, заявка не уйдёт дважды.
- **Антифлуд** — не больше `APPLICATIONS_PER_HOUR` доставленных заявок в час на аккаунт (скользящее окно, `bot/services/rate_limit.py`); неудачные отправки лимит не расходуют.
- **Команды на текстовом шаге** (`/foo`) не принимаются как ответ — «Такой команды нет».
- **Повторы отправки вам** (`bot/services/notifier.py`): сеть и 5xx — до 3 попыток с паузами `SEND_RETRY_DELAYS`; flood control — ждём сколько сказал Telegram, но не больше 30 с; 400/403 — без повторов. Не доставлено — клиенту сообщение с `FALLBACK_CONTACT`, сводка с «Отправить» остаётся.
- **Ошибки** — глобальный обработчик (`bot/handlers/errors.py`): клиенту нейтральное «Что-то пошло не так…», в лог — тип и трейсбек; заблокировавший бота клиент — INFO без трейсбека.

## Администратор: уведомления, панель, статусы

**Уведомление о заявке** — «Новая заявка № …»: время (в `TIMEZONE`), источник, имя, контакт, тип, задача, Telegram-данные клиента (id, ник, имя-упоминание). Кнопки:
- «Написать клиенту» — ссылка: ник из профиля → ник из контакта → `tg://user?id=` (если Telegram такую кнопку не принимает из-за приватности клиента, заявка уходит без неё);
- «✅ В работу» — ставит статус в базе и отметку «✅ В работе с …» в сообщении (одно и то же время), кнопка исчезает. Нажать может только `ADMIN_ID`. Если заявку уже закрыли в панели, отметка не ставится — всплывает её статус. Если база недоступна, отметка ставится, статус не пишется, вам приходит «⚠️ … статус «В работе» не записан в базу».

**Статусы** — новая → в работе → выполнена, или отменена. Разрешённые переходы заданы в одном месте — `ALLOWED_TRANSITIONS` в `bot/models.py`:

| Сейчас | Можно |
|---|---|
| новая | в работу, отменить |
| в работе | завершить, отменить, вернуть в новые |
| выполнена, отменена | вернуть в новые |

Смена статуса атомарна (`UPDATE … WHERE status = <текущий>`), повтор того же действия ничего не меняет и время не сдвигает; «Вернуть в новые» сбрасывает время взятия и закрытия. Отменённая заявка из базы **не удаляется**.

**Панель `/admin`** (`bot/handlers/panel.py`) — только у `ADMIN_ID` и только в личном чате; у остальных `/admin` отвечает как любая неизвестная команда:
- главный экран: «🆕 Новые (N)», «🔧 В работе (M)», «✅ Выполненные (K)», «🚫 Отменённые (C)», «📋 Все»;
- список по 5 заявок: номер, дата, имя, тип проекта, значок статуса (контакт и задача — только в карточке); «‹ назад» / «вперёд ›», «⌂ В панель»;
- карточка — как уведомление о заявке, плюс статус и время; «Написать клиенту», кнопки переходов из таблицы, «‹ К списку»; «🚫 Отменить» спрашивает подтверждение («Да, отменить» / «Нет»);
- все экраны — правка одного сообщения; база недоступна — панель так и пишет.

**Одна актуальная панель.** Повторный `/admin` удаляет прежнюю панель и само сообщение с командой и присылает новую. Бот помнит панель в памяти: после перезапуска старая остаётся в чате, но её кнопки работают (и она становится текущей). Кнопки заменённой панели отвечают «Эта кнопка уже неактуальна».

**Уведомление клиенту «принята в работу»** (`bot/services/client_notifier.py`) — только при переходе новая → в работе (кнопкой под уведомлением или в панели), картинкой `in_work.jpg` с подписью «🔧 Заявка № … принята в работу / Эдуард начал её рассматривать и свяжется с вами по указанному контакту.». Подтверждения перед «В работу» нет — нажатие сразу пишет клиенту.
- **Один раз за жизнь заявки:** перед отправкой атомарно ставится метка `client_notified_at`; двойное нажатие, гонка двух нажатий, «Вернуть в новые» → «В работу» второго сообщения не дают.
- **Не дошло** — вам «Клиенту по заявке № … сообщение о взятии в работу не доставлено (<класс ошибки>)»; статус и отметка остаются. Клиент заблокировал бота или чат не найден — метка остаётся (повтор бесполезен). Сбой сети или Telegram — метка снимается: следующий переход в работу отправит снова. Прочие ошибки — метка остаётся (без дубля).
- Не ушла только картинка, а текст дошёл — это доставка, вам ничего не приходит.
- **Базы нет или заявки в ней нет** — клиенту не пишем (нечем защититься от повторов), всплывашка говорит «клиенту не сообщено».

**Сообщения о базе:** при запуске — строка о базе; не удалось записать заявку — «⚠️ Заявка … не сохранена в базу (…)» сразу после самой заявки (не чаще раза в час на один класс ошибки, в логе — каждый случай); не удалось записать статус — «⚠️ … статус … не записан в базу».

## Картинки и оформление

**Картинки** (`bot/assets/`, 1280×720, до 300 КБ — проверяет `tests/test_media.py`) уходят клиенту фото с подписью; администратору картинок нет:

| Файл | Когда |
|---|---|
| `welcome.jpg` | приветствие на `/start` |
| `accepted.jpg` | «✅ Заявка принята» — после доставки заявки вам |
| `in_work.jpg` | «🔧 Заявка № … принята в работу» |

Файл загружается в Telegram один раз, дальше — по `file_id` (кэш в памяти, `bot/services/media.py`). Если фото не ушло (нет файла, отказ Telegram, сеть, подпись длиннее 1024 символов) — тот же текст с теми же кнопками приходит обычным сообщением.

**Пересборка** — HTML-шаблоны `tools/images/*.html` → Google Chrome headless → PNG → JPEG (`sips`, есть в macOS):

```bash
sh tools/images/build.sh           # все три
sh tools/images/build.sh in_work   # только перечисленные: welcome, accepted, in_work
```

Нужны Google Chrome в `/Applications` и сайт рядом с ботом (`../ferz-site`): шрифты и портрет берутся оттуда, не копируются. Палитра (бордо, золото) — числа из `main.css` сайта в `tools/images/common.css`; при смене сезона сайта картинки нужно пересобрать.

**Цвета кнопок** — поле `style` inline-кнопки, значения — `ButtonStyle` в `bot/keyboards.py`. Telegram даёт только три: `primary` (синий), `success` (зелёный), `danger` (красный); своих цветов нет, а старые версии приложений цвет не показывают — кнопка обычная.

| Цвет | Кнопки |
|---|---|
| зелёный | «Оставить заявку», «Даю согласие», «Отправить», «✅ Завершить» |
| синий | «✅ В работу» под заявкой, «🔧 В работу» в панели |
| красный | «🚫 Отменить», «Да, отменить» |

Остальные — без цвета. Клиентские тексты — HTML (жирные заголовки, номер `<code>`, задача в сводке цитатой), все в `bot/texts.py`.

**Описание бота** в профиле Telegram (`BOT_DESCRIPTION` — «Что умеет этот бот?» в пустом чате, `BOT_SHORT_DESCRIPTION` — профиль и превью ссылки) бот ставит сам при каждом старте; сбой — предупреждение в логе, бот работает. Имя бота не меняется.

## База данных

**Где:** `data/bot.db` в папке проекта (`DATABASE_PATH`). Папка создаётся при первом запуске с правами `700`, новый файл — `600` (права существующего файла бот не меняет). Режим WAL: рядом лежат `bot.db-wal` и `bot.db-shm` — это нормально; читать базу можно при работающем боте.

**Схема** — одна таблица `applications`, строка на заявку (комментарии к столбцам видны в DDL):

| Столбец | Что это |
|---|---|
| `id` | номер заявки `ГГММДД-XXXX` (дата — в `TIMEZONE`), первичный ключ |
| `created_at` | время первой попытки отправки, UTC, `2026-10-19T07:15:03Z` |
| `source` | `site` — по ссылке с сайта, `bot` — сам |
| `name`, `contact`, `task` | как обращаться, почта/`@ник`, задача |
| `project_type` | `site`, `landing`, `bot`, `service`, `shop`, `other` |
| `consent` | согласие на обработку данных, всегда `1` |
| `applicant_user_id`, `applicant_username`, `applicant_full_name` | Telegram-отправитель: id, ник без `@`, имя из профиля |
| `delivered_at` | когда заявка дошла до вас, UTC; `NULL` — не дошла |
| `status` | `new`, `in_work`, `done`, `cancelled` |
| `taken_at`, `closed_at` | взята в работу / выполнена или отменена, UTC; иначе `NULL` |
| `client_notified_at` | когда клиенту ушло «принята в работу», UTC; `NULL` — не сообщали |

Заявка пишется **до** отправки вам — в базе есть и недоставленные. Повтор отправки той же заявки строку не дублирует и отметку о доставке не сбрасывает.

**Миграции** — `MIGRATIONS` в `bot/services/sqlite_repository.py`, версия — `PRAGMA user_version` (сейчас **4**). При запуске недостающие миграции применяются по очереди, каждая в своей транзакции; база от более новой версии бота — ошибка `SchemaError`. Новый столбец — новая строка в конец `MIGRATIONS`, старые не меняются.

**Если база не открылась** (права, повреждённый файл) — бот работает без неё: заявки только пересылаются вам, вы получаете «⚠️ База данных недоступна…».

**DBeaver:** новое подключение → SQLite → Path `<папка проекта>/data/bot.db`. Работайте в режиме **авто-коммита** (он по умолчанию): незавершённая транзакция с изменениями держит базу — бот ждёт до 5 секунд и заявку не записывает; `VACUUM` в ручном режиме не выполняется. Статус лучше менять кнопками бота: правка `status` вручную не проверяет переходы и не ставит время (недопустимое значение не пропустит CHECK).

**Резервная копия** при работающем боте — только так (копирование файлов во время записи может дать испорченную копию):

```bash
sqlite3 data/bot.db ".backup data/copy.db"
```

**Запросы** (время в базе UTC, `+5 hours` — Челябинск):

```sql
-- Все заявки, свежие сверху:
SELECT id, datetime(created_at, '+5 hours') AS created_local,
       datetime(delivered_at, '+5 hours') AS delivered_local, status, name, contact
FROM applications ORDER BY created_at DESC;

-- Сколько заявок в каждом статусе:
SELECT status, count(*) AS n FROM applications GROUP BY status;

-- В работе дольше 7 дней:
SELECT id, name, contact, datetime(taken_at, '+5 hours') AS taken_local
FROM applications
WHERE status = 'in_work'
  AND taken_at < strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-7 days')
ORDER BY taken_at;

-- В работе, но клиенту не сообщили (временный сбой или взяты в работу до этапа 2в):
SELECT id, name, contact FROM applications
WHERE status = 'in_work' AND client_notified_at IS NULL;

-- Недоставленные вам заявки (клиенту нужно ответить самому):
SELECT id, created_at, name, contact, task
FROM applications WHERE delivered_at IS NULL ORDER BY created_at DESC;
```

**Срок хранения и удаление данных клиента.** Политика сайта обещает хранить не дольше 1 календарного года после последнего сообщения и удалять по запросу. Автоудаления нет — вручную (DBeaver или `sqlite3 data/bot.db`):

```sql
-- 1. Найти все заявки человека: по почте/нику из заявки или по Telegram id/нику
--    (контакт-ник хранится с «@», applicant_username — без «@»).
SELECT id, created_at, name, contact, applicant_user_id, applicant_username
FROM applications
WHERE lower(contact) = lower('anna@example.com')
   OR lower(contact) = lower('@anna_k')
   OR applicant_user_id = 123456789
   OR lower(applicant_username) = lower('anna_k');

-- 2. Удалить — ровно с тем же условием WHERE.
DELETE FROM applications
WHERE lower(contact) = lower('anna@example.com')
   OR lower(contact) = lower('@anna_k')
   OR applicant_user_id = 123456789
   OR lower(applicant_username) = lower('anna_k');

-- 3. Стереть удалённое физически. Порядок важен: VACUUM пишет чистую копию
--    в bot.db-wal, checkpoint переносит её в bot.db и очищает -wal.
VACUUM;
PRAGMA wal_checkpoint(TRUNCATE);

-- Кандидаты на удаление по сроку (старше года):
SELECT id, created_at, name, contact FROM applications
WHERE created_at < strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-1 year');
```

Срок считается от **последнего сообщения** переписки, а её в базе нет — перед удалением проверьте, не продолжается ли общение. `lower()` в SQLite меняет регистр только у латиницы. Резервные копии (Time Machine, `.backup`) этими командами не очищаются.

**Почему так:**
- **Слои.** Хендлеры (`handlers/`) тонкие: принимают апдейт, вызывают сервисы (`services/`), отвечают. Логика без Telegram-разметки — в `models.py` и `services/`, поэтому её можно проверить без бота и переиспользовать (например, для писем с сайта).
- **Тексты в одном месте** (`texts.py`), а пользовательский ввод попадает в HTML только через `services/formatting.py` — одно место, где экранирование нельзя забыть.
- **Зависимости через `workflow_data`** (`dp["repository"] = …` в `bot/app.py`): хендлер получает их по имени параметра, а тесты подменяют любую — базу, отправку картинок, часы.
- **Роутеры — фабрики** (`create_router()`): aiogram не даёт подключить один роутер к двум диспетчерам, а тестам нужен свежий диспетчер на каждый тест. Порядок роутеров — в `handlers/__init__.py`.
- **Хранилище — протокол** `ApplicationRepository`: хендлеры не знают про SQLite; без базы работает `NullRepository`.

## Тесты и качество

```bash
.venv/bin/python -m pytest              # все тесты: без сети и без настоящего токена
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/mypy                          # строгая проверка типов пакета bot
```

Отдельные тесты:

```bash
.venv/bin/python -m pytest tests/test_panel.py                 # один файл
.venv/bin/python -m pytest -k "pagination"                     # по имени
.venv/bin/python -m pytest -W error::ResourceWarning           # незакрытые соединения — ошибка
```

**Как устроены тесты** (`tests/conftest.py`):
- `MockSession` подменяет HTTP-сессию aiogram: каждый вызов Bot API записывается в `session.requests`, ответ — правдоподобный объект (сообщение с `message_id`, фото с `file_id`). Ведёт себя как Telegram там, где это важно: правка текста у фото-сообщения падает. Хук `session.hook` имитирует сбои (`TelegramNetworkError`, `Forbidden` и т. д.).
- `FakeUser` пишет боту и нажимает кнопки; апдейты идут через `dp.feed_update` — тот же путь, что из long polling. Диспетчер собирается той же `create_dispatcher`, что в боевом запуске.
- Базы — только во временных папках pytest (`DATABASE_PATH` подменяется для всех тестов), `data/` тесты не трогают.

**Мутационная проверка** — способ проверить сами тесты: в код вносится намеренная ошибка (убрать проверку админа, снять `WHERE status = ?`, отправить подтверждение до доставки…), прогоняются тесты — они обязаны упасть; файл возвращается. Если мутация «выжила», тест дописывается. Скрипты мутаций лежат во временной папке исполнителя, итоги по этапам — в [`STATUS.md`](STATUS.md).

## Безопасность и приватность

- **Секреты** — только в `.env` (в `.gitignore`); в репозитории — `.env.example`. Токен хранится как `SecretStr` и не попадает в `repr`, ошибки настроек и логи: `RedactingFormatter` вырезает его из любой строки лога, включая трейсбеки.
- **Логи без персональных данных:** id пользователей, номера заявок, длины, классы ошибок; без имён, контактов и текстов задач. Значения из чужих `callback_data` пишутся через `%r` — перевод строки не подделает строку лога.
- **Экранирование:** весь ввод клиента и данные Telegram-профиля проходят `html.escape` в `services/formatting.py`; SQL — только параметризованные запросы.
- **Доступ:** «В работу» и все кнопки панели проверяют `from_user.id == ADMIN_ID` (не чат); посторонний `/admin` неотличим от неизвестной команды.
- **Что и где хранится:** заявки с персональными данными — в `data/bot.db` открытым текстом (права `700`/`600`, в git не попадает). Шаги диалога и антифлуд — в памяти процесса. Подробнее про удаление — [База данных](#база-данных).

## Известные ограничения

- Шаги диалога (FSM) и антифлуд — в памяти: после перезапуска незавершённые диалоги теряются, счётчики обнуляются.
- Если Telegram доставил сообщение, а ответ потерялся, возможен дубль: заявки у вас (узнаётся по тому же номеру) или картинки с текстом у клиента.
- После перезапуска бот не помнит текущую панель — старая остаётся в чате; кэш `file_id` картинок тоже пустеет (первая отправка снова загружает файл).
- Номер заявки — дата + 4 случайных hex-символа: совпадение возможно (редко); заявка другого человека с тем же номером в базу не запишется, вы получите уведомление.
- Срок хранения 1 год — автоудаления нет (вручную, см. [База данных](#база-данных)).
- Отменённой/выполненной в панели заявке кнопка «✅ В работу» под старым уведомлением не исчезает (нажатие честно покажет статус).
- **Не проверялось:** вид в разных клиентах Telegram (цвета кнопок, картинки, описание бота), Windows, Python 3.12–3.13.

Полный список долга — в [`STATUS.md`](STATUS.md).

## Устранение неполадок

| Сообщение / симптом | Что делать |
|---|---|
| `Ошибка настройки: Не найден BOT_TOKEN…` / `…заполнен неверно…` (код 2) | проверьте `.env`: токен целиком, без кавычек и пробелов; `ADMIN_ID` — число |
| `Telegram отклонил токен (Unauthorized)…` (код 1) | токен устарел или отозван — скопируйте актуальный из @BotFather |
| `Нет связи с Telegram (…)` (код 1) | нет интернета или Telegram недоступен — запустите снова |
| `Не удалось написать администратору (ADMIN_ID): … chat not found` | откройте своего бота и нажмите /start, проверьте `ADMIN_ID` (@userinfobot) |
| `Failed to fetch updates - TelegramConflictError: … terminated by other getUpdates request` | запущены две копии бота с одним токеном — остановите лишнюю |
| `База заявок не открылась (…)… Бот работает БЕЗ сохранения заявок в базу` и «⚠️ База данных недоступна» в Telegram | проверьте путь `DATABASE_PATH` и права на папку/файл; при `SchemaError` — база от более новой версии бота |
| «⚠️ Заявка … не сохранена в базу (OperationalError)» | база занята (например, незакоммиченная правка в DBeaver) — включите авто-коммит |
| `Заявка … НЕ доставлена администратору…` | клиенту ушёл запасной контакт; заявка есть в базе с `delivered_at IS NULL` |
| `Картинка … не отправлена (…) — отправляю текстом` | клиент получил текст без картинки; при `FileNotFoundError` — нет файла в `bot/assets/`, пересоберите картинки |
| `Не удалось установить описание бота / меню команд…` | бот работает; при следующем старте попробует снова |
| Кнопки без цвета | старая версия приложения Telegram — цвета не поддерживаются, это нормально |
| `build.sh`: `Нет Google Chrome…` / `Нет сайта рядом с ботом…` | нужен Google Chrome в `/Applications` и `../ferz-site` рядом с ботом |
