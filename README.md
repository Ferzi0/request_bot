# ferz-bot

Telegram-бот приёма заявок для сайта Эдуарда Торгашова (Ferz). Python 3.12–3.14, aiogram 3, long polling.
Подробный README — на этапе 2; решения и история — в `STATUS.md`.

## Запуск

```bash
# 1. Окружение (зависимости зафиксированы в uv.lock)
uv sync                       # создаст .venv и поставит всё, включая dev-инструменты
# без uv:  python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

# 2. Настройки
cp .env.example .env          # впишите BOT_TOKEN и ADMIN_ID

# 3. Старт (Ctrl+C — остановка)
.venv/bin/python -m bot
```

Перед первым запуском откройте своего бота в Telegram и нажмите /start — иначе бот не сможет прислать вам заявку.

## Проверки

```bash
.venv/bin/python -m pytest    # тесты без сети и без настоящего токена
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/mypy                # строгая проверка типов пакета bot
```

После изменения зависимостей: `uv lock && uv export --format requirements-txt --no-dev --no-hashes -o requirements.txt`.

## База данных

Каждая отправленная заявка сохраняется в SQLite: **`data/bot.db`** в папке проекта (путь меняется настройкой `DATABASE_PATH` в `.env`). Папка `data/` создаётся при первом запуске с правами только для владельца (`700`, новый файл базы — `600`; права уже существующего файла бот не меняет) и в git не попадает. Рядом лежат служебные `bot.db-wal` и `bot.db-shm` — это нормально (режим WAL); копию при работающем боте делайте командой `sqlite3 data/bot.db ".backup data/copy.db"` (простое копирование файлов во время записи может дать испорченную копию) или остановите бота и скопируйте `bot.db`.

Что хранится — одна таблица `applications`, по строке на заявку (комментарии к столбцам видны в DDL таблицы):

| Столбец | Что это |
|---|---|
| `id` | номер заявки `ГГММДД-XXXX` (тот же, что в Telegram), первичный ключ |
| `created_at` | время отправки, **UTC**, `2026-10-19T07:15:03Z` |
| `source` | `site` — пришёл по ссылке с сайта, `bot` — сам |
| `name`, `contact`, `task` | как обращаться, почта/@ник, задача |
| `project_type` | `site`, `landing`, `bot`, `service`, `shop`, `other` |
| `consent` | согласие на обработку данных, всегда `1` |
| `applicant_user_id`, `applicant_username`, `applicant_full_name` | Telegram-отправитель: id, ник без `@`, имя из профиля |
| `delivered_at` | когда заявка дошла до вас в Telegram, UTC; `NULL` — не дошла (клиенту показан запасной контакт) |
| `status` | `new` — новая, `in_work` — в работе, `done` — выполнена, `cancelled` — отменена (строка остаётся) |
| `taken_at` | когда взята в работу, UTC; `NULL` у новой |
| `closed_at` | когда выполнена или отменена, UTC; иначе `NULL` |
| `client_notified_at` | когда клиенту ушло «заявка принята в работу», UTC; `NULL` — не сообщали |

Заявка записывается в базу **до** отправки вам, поэтому в базе есть и недоставленные заявки (`delivered_at IS NULL`). Повторная отправка той же заявки (после сбоя доставки) не создаёт вторую строку и не сбрасывает отметку о доставке. Номер заявки строится по дате в поясе `TIMEZONE`, а время в столбцах — UTC.

Схема версионируется (`PRAGMA user_version`, сейчас 4): при запуске бот сам доводит старую базу до текущей версии, данные сохраняются.

**Если с базой что-то не так, бот сообщает вам в Telegram**, а заявки продолжают приходить:
- при запуске — строка о базе в пробном сообщении («База данных: работает (схема v4, заявок: N).» или «⚠️ База данных недоступна…» с классом ошибки). Если `NOTIFY_ADMIN_ON_START=false`, пробного сообщения нет, но о недоступной базе бот всё равно напишет;
- если заявку не удалось записать — «⚠️ Заявка … не сохранена в базу (…)» сразу после самой заявки; не чаще раза в час на один вид ошибки, в логе — каждый случай. Если не дошла и сама заявка, уведомления нет (оно бы тоже не дошло) — только лог.

- если не удалось записать статус после кнопки «✅ В работу» — «⚠️ Заявка …: статус «В работе» не записан в базу (…)». Отметка в сообщении при этом стоит.

### Статусы заявок и админ-панель

У каждой заявки в базе есть статус: **новая → в работе → выполнена**, или **отменена**. Разрешённые переходы (заданы в одном месте — `ALLOWED_TRANSITIONS` в `bot/models.py`):

| Сейчас | Можно |
|---|---|
| новая | в работу, отменить |
| в работе | завершить, отменить, вернуть в новые |
| выполнена, отменена | вернуть в новые |

«Вернуть в новые» сбрасывает время взятия в работу и закрытия. Повторное нажатие того же действия ничего не меняет (время не сдвигается). Отменённая заявка из базы **не удаляется**. Клиенту пишем только об одном: что заявку взяли в работу (ниже); о завершении, отмене и возврате в новые — ничего.

Кнопка **«✅ В работу»** под сообщением о новой заявке теперь ставит и статус в базе — с тем же временем, что в отметке «✅ В работе с …». Если заявку уже закрыли в панели, отметка не ставится, а всплывает подсказка с её статусом.

**Админ-панель — команда `/admin`** (только для вас: у остальных `/admin` отвечает как любая неизвестная команда; пункт «Админ-панель» в меню команд виден только в вашем чате, если Telegram это принял при запуске бота):
- главный экран: «🆕 Новые (N)», «🔧 В работе (M)», «✅ Выполненные (K)», «🚫 Отменённые (C)», «📋 Все»;
- список — по 5 заявок: номер, дата (по `TIMEZONE`), имя, тип проекта, значок статуса; контакт и задача — только в карточке; «‹ назад» / «вперёд ›», «⌂ В панель»;
- карточка — как сообщение о заявке, плюс статус и время; кнопки «Написать клиенту», смены статуса по таблице выше, «‹ К списку». «🚫 Отменить» спрашивает подтверждение («Да, отменить» / «Нет»);
- все экраны — правка одного сообщения, чат не засоряется. Если база недоступна, панель так и пишет.

Статус лучше менять кнопками бота: правка `status` вручную в DBeaver не проверяет переходы и не ставит время (недопустимое значение база не примет — стоит CHECK).

### Уведомление клиенту «заявка принята в работу»

Когда заявка переходит из «новой» в «в работе» — кнопкой «✅ В работу» под сообщением о заявке или в панели, — клиенту в Telegram приходит:

> 🔧 **Заявка № `261020-676A` принята в работу**
> Эдуард начал её рассматривать и свяжется с вами по указанному контакту.

Подтверждения перед «В работу» нет (решение заказчика): нажатие сразу пишет клиенту.

- **Один раз за жизнь заявки.** Перед отправкой бот ставит в базе метку `client_notified_at` одним атомарным запросом; второе нажатие, двойной тап или «Вернуть в новые» → «В работу» второго сообщения не дают.
- **Не дошло** — вам приходит «Клиенту по заявке № … сообщение о взятии в работу не доставлено (<класс ошибки>)». Статус и отметка в сообщении при этом стоят.
  - клиент заблокировал бота / чат не найден — метка остаётся (повтор бесполезен);
  - сбой сети или Telegram — метка снимается: следующий переход в работу («Вернуть в новые» → «В работу») отправит сообщение снова;
  - любая другая ошибка (неизвестно, дошло ли) — метка остаётся, чтобы не было дубля.
- **Базы нет или заявки в ней нет** — клиенту не пишем (без метки нечем защититься от повторов); всплывашка после «В работу» говорит «клиенту не сообщено».
- Заявкам, взятым в работу до этого обновления, сообщение не уходит.

### Как смотреть в DBeaver

Новое подключение → SQLite → Path: `<папка проекта>/data/bot.db` → Finish. Читать можно при работающем боте. Время в базе — UTC; по Челябинску:

```sql
SELECT id, datetime(created_at, '+5 hours') AS created_local,
       datetime(delivered_at, '+5 hours') AS delivered_local, name, contact
FROM applications ORDER BY created_at DESC;

-- Сколько заявок в каждом статусе:
SELECT status, count(*) AS n FROM applications GROUP BY status;

-- Новые заявки, свежие сверху:
SELECT id, datetime(created_at, '+5 hours') AS created_local, name, project_type
FROM applications WHERE status = 'new' ORDER BY created_at DESC;

-- В работе дольше 7 дней (число дней меняйте в '-7 days'):
SELECT id, name, contact, datetime(taken_at, '+5 hours') AS taken_local
FROM applications
WHERE status = 'in_work'
  AND taken_at < strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-7 days')
ORDER BY taken_at;

-- В работе, но клиенту не сообщили (временный сбой сети/Telegram или взяты в работу
-- до обновления; заблокировавшие бота сюда не попадают — у них метка стоит):
SELECT id, name, contact, datetime(taken_at, '+5 hours') AS taken_local
FROM applications WHERE status = 'in_work' AND client_notified_at IS NULL;

-- Выполнено за последние 30 дней:
SELECT count(*) FROM applications
WHERE status = 'done' AND closed_at >= strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-30 days');

-- Недоставленные заявки (Telegram отказал — клиенту нужно ответить самому):
SELECT id, created_at, name, contact, task
FROM applications WHERE delivered_at IS NULL ORDER BY created_at DESC;
```

Работайте в режиме **авто-коммита** (в DBeaver он включён по умолчанию — переключатель Auto-Commit на панели). В ручном режиме коммита незавершённая транзакция с изменениями (например, `DELETE` без Commit) держит базу: бот ждёт до 5 секунд и заявку в базу не записывает (придёт уведомление «не сохранена»). Кроме того, `VACUUM` в ручном режиме не выполняется («cannot VACUUM from within a transaction»). После правок — Commit или вернитесь в авто-коммит; вкладку с результатами запроса лучше закрыть перед `wal_checkpoint`.

### Как найти и удалить данные клиента

Политика сайта обещает: хранить не дольше 1 календарного года после последнего сообщения и удалять по запросу. Автоудаления пока нет — делается вручную (DBeaver или `sqlite3 data/bot.db` в Терминале).

```sql
-- 1. Найти все заявки человека: по почте/нику из заявки или по Telegram id/нику.
--    (контакт-ник хранится с «@», applicant_username — без «@»)
SELECT id, created_at, delivered_at, name, contact, applicant_user_id, applicant_username
FROM applications
WHERE lower(contact) = lower('anna@mail.ru')
   OR lower(contact) = lower('@anna_k')
   OR applicant_user_id = 123456789
   OR lower(applicant_username) = lower('anna_k');

-- 2. Удалить их — ровно то же условие WHERE, что в поиске выше.
DELETE FROM applications
WHERE lower(contact) = lower('anna@mail.ru')
   OR lower(contact) = lower('@anna_k')
   OR applicant_user_id = 123456789
   OR lower(applicant_username) = lower('anna_k');

-- 3. Стереть удалённое физически: иначе остатки могут лежать в свободных
--    страницах файла и в bot.db-wal. Порядок важен: VACUUM пишет чистую копию
--    в bot.db-wal, а checkpoint переносит её в bot.db и очищает -wal
--    (при работающем боте без checkpoint старые страницы остались бы в bot.db).
VACUUM;
PRAGMA wal_checkpoint(TRUNCATE);

-- Заявки старше года (кандидаты на удаление по сроку хранения):
SELECT id, created_at, delivered_at, name, contact
FROM applications
WHERE created_at < strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-1 year');
```

Срок по политике считается от **последнего сообщения** в переписке, а её в базе нет — перед удалением старых заявок проверьте, не продолжается ли общение. Копии базы в резервных копиях (Time Machine) этими командами не удаляются.
